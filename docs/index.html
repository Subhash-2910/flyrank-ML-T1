Transparent Refresh Opportunity Scoring for Content Review

A client-grouped and leakage-audited study of which pseudonymized content pages should be prioritized for human review.

Author: Subhash Kashyap Lane: Refresh / Content Opportunity Scoring Dataset: 30,000 content records Validation: Client-grouped
Abstract Problem Data Methodology Results Recommendations Limits Reproducibility

Abstract

This project asks which content pages should be prioritized for human review when a content team has limited capacity. It uses the FlyRank ML Internship anonymized starter dataset, containing 30,000 pseudonymized content records across 32 clients. I compared a transparent stale-and-visible baseline with Logistic Regression and then re-ran the model with a stricter client-grouped, leakage-audited design. In the initial same-split comparison, Logistic Regression reached Precision@20 of 80.0% versus 45.0% for the baseline; under the stricter grouped validation, Precision@20 was 50.0%. The output is a ranked, human-reviewed action queue that supports content review decisions and does not claim that refreshing a page causes improved search performance.

Introduction / problem statement

Content teams cannot inspect every page at once. This project supports a practical decision: which pages should a human review first for possible refresh work?

Unit and output

The unit of analysis is one pseudonymized content page. The output is a ranked review queue with an action label, reason code, and model score.

Cost of a wrong call

A false positive can waste editorial time. A false negative can leave a potentially important page unreviewed. The tool therefore supports prioritization, not automatic action.

Dataset

The analysis uses data/raw/content_refresh_anonymized.csv from the FlyRank ML Internship starter release. It contains anonymized numeric and categorical content-performance signals.

What was excluded

  • content_id and client_id were used only for identification and grouped validation, never as model features.
  • trend_direction was the outcome label and was excluded from features.
  • trend_pct was excluded because it directly measures the same observed trend outcome.
  • 30-day comparison-window fields and 90-day performance totals were excluded from the strict audit because they may overlap with the measured trend period.
  • No client names, domains, URLs, titles, raw queries, credentials, or private exports appear in this paper.
Public-safety boundary: this paper reports only aggregated results and pseudonymized analysis. It does not disclose client-identifying information.

Methodology

Observed outcome

The retrospective outcome is whether a page’s observed trend_direction was down. This is an observed historical pattern, not a label for whether a future refresh will succeed.

Baseline

The transparent Week-4 baseline assigned 60% weight to relative content age/staleness and 40% weight to current 90-day impressions. It assigned selected pages the reason code STALE_VISIBLE_PAGE.

Model and strict feature set

Logistic Regression was selected because it is transparent, quick to train, and suitable for an explainable ranking workflow. The stricter leakage-audited feature set used search volume, competition, CPC, word count, character count, content age, days since update, competition level, content type, and main intent.

Validation design

The final audit used a client-grouped 80/20 split. All pages from a client appeared only in training or testing, never both. This is more conservative than a random page-level split because it tests whether the model generalizes to previously unseen clients.

How to read the results: the 80.0% initial result came from a broader feature set. The stricter client-grouped and leakage-audited result is the primary final estimate because it uses a more cautious feature definition.

Error analysis

False positives were pages assigned a higher downward-trend score that did not have an observed down trend. False negatives were pages with an observed downward trend but a lower predicted score. Likely explanations include seasonality, changing search intent, competition, and client-specific context that was not available in the strict feature set.

In total, 2,129 of 6,163 held-out pages (34.54%) were marked REVIEW_FOR_REFRESH. Every recommendation requires a human to inspect intent, factual accuracy, freshness, seasonality, indexing, competition, and editorial value before acting.

Limitations and honest framing

  • The model measures observed associations in one anonymized starter dataset.
  • It does not predict Google’s algorithm.
  • It does not prove that refreshing a page will improve performance.
  • The stricter grouped result is modest, so the model should be treated as a limited decision-support aid.
  • No action should be automated: do not automatically rewrite, publish, delete, merge, prune, change metadata, or alter URLs.
  • Review or retrain if the data mix changes, the outcome definition changes, Precision@20 materially changes, or editors repeatedly flag weak recommendations.
